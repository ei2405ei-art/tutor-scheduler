# ТЗ на MVP «Планировщик занятий репетитора»

Статус: **утверждён владельцем продукта, MVP реализован**.
Источник: `Планировщик занятий репетитора.docx`, `Проверка ИИ.docx`.
Область продукта: локальное расписание занятий частного репетитора.

## 1. Назначение

MVP проверяет гипотезу: репетитор, который держит всё расписание в одном месте,
перестаёт путаться в переносах и терять договорённости с учениками.

Результат MVP — недельный вид расписания, в котором занятие переносится или
отменяется одним действием, а по каждому ученику видно, сколько занятий оплачено,
сколько проведено и сколько осталось.

Целевой пользователь: частный репетитор с 5–30 учениками, который сейчас ведёт
расписание в заметках и чатах.

## 2. Паспорт проекта

- Уровень: Старт · Сервис
- Для кого: частный репетитор
- Результат: расписание занятий. Напоминания вынесены в P1 (см. A9)
- Ориентир по трудозатратам: 8–10 часов в неделю
- Пользовательская формулировка: «Как репетитор, я хочу видеть все занятия недели
  и быстро переносить их, чтобы не путаться в договорённостях»

## 3. Проблема клиента

Репетитор ведёт расписание в заметках и забывает о переносах. Договорённости
рассыпаются по мессенджерам, свободное время не видно, а по деньгам нет ответа
на вопрос «сколько ученик ещё должен».

## 4. Допущения и утверждённые решения

| # | Допущение | Решение |
|---|---|---|
| A1 | Формат — приложение, которым репетитор пользуется сам | Браузерная PWA: HTML/JS + `localStorage`, публикация на GitHub Pages |
| A2 | В системе один пользователь | Без аккаунтов, авторизации, ролей и прав |
| A3 | Ученик не входит в систему | Ученик — только запись в справочнике, без входа |
| A4 | Оплата выглядит как пакет занятий | Ученик оплачивает N занятий вперёд; баланс = оплачено − проведено |
| A5 | Баланс должен быть честным | Списывается только проведённое занятие; перенос и отмена баланс не трогают |
| A6 | У репетитора есть и регулярные, и разовые занятия | В MVP поддержаны оба типа: серия и разовое занятие |
| A7 | Неделя нужна стандартная | Границы недели: Пн–Вс. Серия может занимать все 7 дней |
| A8 | Ставка — цена одного занятия | Длительность в часах не используется. `durationMin` хранится только для отображения интервала и защиты от пересечений. `rate` участвует в недельном итоге: сумма к оплате и долг |
| A9 | В брифе результатом заявлены «расписание и напоминания» | Напоминания вынесены в P1/P2, в MVP не реализуются. Паспорт приведён в соответствие |
| A10 | Данные не должны уходить в сеть | Хранение полностью локальное, без сервера и внешних интеграций |
| A11 | Контакт ученика один | Одно текстовое поле: телефон, Telegram или почта |
| A12 | Серию нужно поддерживать без ручного создания каждого занятия | Горизонт генерации серии — 4 недели вперёд, продление вручную |
| A13 | Расписание смотрят со смартфона | Интерфейс проектируется под мобильный: работа одной рукой, экран от 320 px |

решениями из §15: деньги в недельном итоге считаются по ставке, напоминания
остаются вне MVP.

## 5. Пользователи и сценарии

### 5.1. Пользователь

Репетитор — единственный пользователь MVP. Ведёт справочник учеников,
расписание и учёт предоплаты.

### 5.2. Основной сценарий

1. Репетитор добавляет ученика: имя, предмет, контакт, ставка.
2. Создаёт занятие: разовое или серию с регулярностью.
3. Открывает недельный вид и видит все занятия недели.
4. Переносит или отменяет занятие.
5. Открывает карточку занятия и пишет, что прошли, и домашнее задание.
6. Отмечает занятие проведённым, предоплата списывается.
7. После перезагрузки страницы все данные остаются на месте.

### 5.3. Дополнительные сценарии

- закрыть серию, чтобы новые занятия не создавались;
- записать оплату: пакет занятий на конкретную дату;
- посмотреть историю переносов занятия;
- отключить ученика от показа в неделе без удаления истории;
- переключиться на прошлую или будущую неделю;
- достроить серию на следующие недели.

## 6. Модель данных

### 6.1. Student — ученик

| Поле | Тип | Обяз. | Назначение |
|---|---|:---:|---|
| `id` | UUID | да | Идентификация |
| `name` | строка | да | Имя ученика |
| `subject` | строка | да | Предмет |
| `contact` | строка | нет | Телефон, Telegram или почта |
| `rate` | число > 0 | да | Цена одного занятия |
| `color` | значение палитры | да | Визуальная идентификация в неделе |
| `active` | булево | да | Показывается ли в недельном виде |
| `createdAt` | дата/время | да | Порядок и аудит |

### 6.2. LessonSeries — серия занятий

| Поле | Тип | Обяз. | Назначение |
|---|---|:---:|---|
| `id` | UUID | да | Идентификация |
| `studentId` | UUID | да | Связь с учеником |
| `weekday` | 1–7 | да | День недели (1 = Пн) |
| `startTime` | `HH:MM` | да | Время начала |
| `durationMin` | число > 0 | да | Длительность, по умолчанию 60 |
| `startsOn` | `YYYY-MM-DD` | да | Дата первого занятия серии |
| `endsOn` | `YYYY-MM-DD` | нет | Ограничение конца серии |
| `active` | булево | да | Генерирует ли серия новые занятия |
| `createdAt` | дата/время | да | Порядок и аудит |

### 6.3. Lesson — занятие

| Поле | Тип | Обяз. | Назначение |
|---|---|:---:|---|
| `id` | UUID | да | Идентификация |
| `studentId` | UUID | да | Связь с учеником |
| `date` | `YYYY-MM-DD` | да | Календарная дата занятия |
| `startTime` | `HH:MM` | да | Время начала |
| `durationMin` | число > 0 | да | Длительность |
| `status` | перечисление | да | `planned` / `done` / `cancelled` / `moved` |
| `topicNote` | строка | нет | Что прошли на занятии |
| `homework` | строка | нет | Домашнее задание |
| `seriesId` | UUID или null | нет | Ссылка на серию; у разового занятия пуст |
| `movedToLessonId` | UUID или null | нет | Куда перенесено занятие |
| `movedFromLessonId` | UUID или null | нет | Откуда занятие перенесено |
| `createdAt` | дата/время | да | Порядок и аудит |
| `updatedAt` | дата/время | да | Порядок и аудит |

Статусы: `planned` — запланировано, `done` — проведено,
`cancelled` — отменено, `moved` — перенесено.

### 6.4. Payment — оплата (пополнение пакета)

| Поле | Тип | Обяз. | Назначение |
|---|---|:---:|---|
| `id` | UUID | да | Идентификация |
| `studentId` | UUID | да | Связь с учеником |
| `lessonsCount` | число > 0 | да | Сколько занятий оплачено |
| `paidAt` | `YYYY-MM-DD` | да | Дата оплаты |
| `comment` | строка | нет | Комментарий к оплате |
| `createdAt` | дата/время | да | Порядок и аудит |

### 6.5. Вычисляемые значения

- **Баланс ученика** = `Σ Payment.lessonsCount` − `count(Lesson where status = done)`
- **Итог недели** = количество запланированных, проведённых, отменённых и
  перенесённых занятий за выбранную неделю, суммарный остаток предоплаты по
  ученикам недели, **сумма к оплате** и **долг**
- **Сумма к оплате за неделю** = `Σ rate` по занятиям недели со статусом
  `planned` или `done`. Занятия со статусом `cancelled` и `moved` не
  учитываются, поэтому перенос попадает в сумму ровно один раз — в неделе
  своей новой даты
- **Долг** = `Σ |balance| × rate` по ученикам недели с отрицательным остатком
  предоплаты

Баланс, сумма к оплате и долг — вычисляемые значения, а не сохранённые поля.
Это исключает рассинхронизацию денег и расписания. Суммы округляются до целых
рублей, валюта отображения — ₽, формат `1 200 ₽`.

Ограничения целостности:

- пара `(seriesId, date)` уникальна — серия не может дать два занятия в один день;
- у разового занятия `seriesId` пуст;
- `movedToLessonId` и `movedFromLessonId` ссылаются только на существующие занятия
  и описывают один перенос в обе стороны;
- дата занятия не раньше `startsOn` своей серии и не позже `endsOn`, если он задан;
- хранится календарная дата, а не произвольный timestamp.

## 7. Бизнес-правила

- **BR-1.** Занятие нельзя создать без ученика, даты и времени. Пустое поле →
  форма не отправляется, показывается понятное сообщение.
- **BR-2.** Слот занят. Два занятия в одну дату с пересекающимися интервалами
  создать нельзя: репетитор один и физически не может вести два занятия.
  Касание границы интервалов пересечением не считается.
- **BR-3.** Генерация серии. Серия создаёт занятия на 4 недели вперёд от `startsOn`
  с учётом `weekday`, `startTime` и `durationMin`. Дни до `startsOn` не создаются.
  Действие «достроить» продлевает горизонт без дублей.
- **BR-4.** Перенос — это перемещение, а не копия. Исходное занятие получает
  статус `moved`, остаётся в своей ячейке недели в приглушённом виде, а новое
  занятие создаётся в целевой дате со связями `movedToLessonId` и
  `movedFromLessonId`. Так выполняется критерий «перенос сразу отражается
  в недельном виде».
- **BR-5.** Перенос сохраняет остальные поля: ученик, время начала, длительность,
  заметка и ДЗ переходят в новое занятие.
- **BR-6.** Перенос не меняет баланс.
- **BR-7.** Перенос в прошлое запрещён: целевая дата не может быть раньше сегодняшней.
- **BR-8.** Отмена необратима. Занятие в статусе `cancelled` нельзя снова перевести
  в `done`. Для возврата работы нужно создать новое занятие.
- **BR-9.** Отмена не меняет баланс.
- **BR-10.** Списание баланса. Перевод занятия в `done` уменьшает баланс ровно на 1.
  Повторный перевод в `done` невозможен, списание не может произойти дважды.
- **BR-11.** Проведённое занятие при нулевом балансе допустимо. Баланс уходит в минус
  и показывается как долг, ученик помечается предупреждением. Операция не блокируется.
- **BR-12.** Статусы необратимы по направлению: `cancelled` и `moved` — конечные.
  `planned` → `done` | `cancelled` | `moved`.
- **BR-13.** Закрытие серии. `active = false` останавливает генерацию; уже созданные
  занятия сохраняются, их статусы и заметки можно менять.
- **BR-14.** Отключение ученика. `active = false` убирает ученика из недельного вида,
  но сохраняет занятия, заметки, оплаты и историю.
- **BR-15.** Баланс ученика всегда пересчитывается из оплат и проведённых занятий.
  Изменение исходных данных и перезагрузка дают один и тот же результат.

## 8. Функциональные требования

### FR-1. Справочник учеников

- **FR-1.1** Создание ученика: имя, предмет, ставка, цвет — обязательны;
  контакт необязателен.
  КА: создание «Иван, Физика, 1200 ₽, контакт не указан» → ученик появляется
  в списке.
- **FR-1.2** Имя обязательно и не может состоять только из пробелов.
  КА: отправка формы с пустым именем отклоняется с сообщением.
- **FR-1.3** Ставка — положительное число.
  КА: ставка 0 или отрицательная отклоняются.
- **FR-1.4** Редактирование полей ученика.
  КА: изменение имени, предмета, контакта и ставки сохраняется после перезагрузки.
- **FR-1.5** Карточка ученика показывает предмет, контакт, ставку, баланс
  «оплачено X − проведено Y = осталось Z», последние занятия и историю оплат.
  КА: после двух проведённых занятий при оплаченных четырёх карточка показывает
  «оплачено 4 − проведён 2 → осталось 2».
- **FR-1.6** Отключение ученика без удаления истории.
  КА: отключённый ученик отсутствует в недельном виде, его прошлое занятие
  и оплаты остаются в карточке.
- **FR-1.7** Предупреждение об исчерпанной предоплате.
  КА: при балансе 0 рядом с именем ученика в неделе видна метка
  «предоплата исчерпана».
- **FR-1.8** Цвет выбирается из фиксированной палитры, произвольный hex не принимается.
  КА: значение вне палитры отклоняется.

### FR-2. Создание занятия

- **FR-2.1** Создание разового занятия: ученик, дата, время, длительность.
  КА: занятие появляется в неделе, содержащей его дату.
- **FR-2.2** Валидация обязательных полей.
  КА: невозможно создать занятие без ученика и без времени — форма не отправляется,
  показывается сообщение.
- **FR-2.3** Защита от пересечения интервалов.
  КА: попытка создать занятие с 16:00 на 90 минут при существующем занятии
  с 16:30 отклоняется.
- **FR-2.4** Создание серии: ученик, день недели, время, длительность, дата старта,
  необязательная дата окончания.
  КА: серия со вторника 18:00 и стартом 01.09.2026 → создаются занятия по вторникам
  на 4 недели вперёд.
- **FR-2.5** Соблюдение `startsOn` и `endsOn`.
  КА: занятия серии не создаются раньше даты старта и позже даты окончания.
- **FR-2.6** Повторный запуск генерации не создаёт дублей.
  КА: после `buildSeries` для уже сгенерированного диапазона количество занятий
  не увеличивается.
- **FR-2.7** «Достроить серию» продлевает горизонт.
  КА: после действия появляются занятия следующих недель без дублей.
- **FR-2.8** Закрытие серии.
  КА: после закрытия новые занятия не создаются, существующие остаются в неделе
  и редактируются.

### FR-3. Недельный вид

- **FR-3.1** Сетка Пн–Вс с заголовком диапазона дат.
  КА: открывается неделя текущей даты, семь колонок на широком экране и семь
  строк на узком.
- **FR-3.2** Переключение недель: предыдущая, следующая, «эта неделя».
  КА: переход на следующую неделю меняет заголовок и состав занятий.
- **FR-3.3** Занятие показывает время, ученика, предмет и цвет ученика.
  КА: карточка занятия различима по времени и имени.
- **FR-3.4** Пустая неделя показывает понятное объяснение и действие создания
  первого занятия.
  КА: в неделе без занятий виден текст и кнопка добавления.
- **FR-3.5** Отменённое занятие визуально отличается и не зависит только от цвета.
  КА: у отменённого занятия есть отдельный паттерн и подпись «отменено».
- **FR-3.6** Перенесённое занятие остаётся в исходной ячейке в приглушённом виде.
  КА: занятие 15.09 числится 15.09 со статусом «перенесено», а его новое
  местоположение — в дате переноса; видны обе карточки.
- **FR-3.7** Итог недели виден на экране: число занятий и сумма к оплате.
  КА: панель показывает «запланировано N, проведено M, отменено K», остаток
  предоплаты по ученикам недели, сумму к оплате в рублях и отдельно долг,
  если баланс отрицательный.
- **FR-3.8** Мобильный вид без горизонтального переполнения на 320 px.
  КА: неделя прокручивается вертикально, основные действия остаются достижимыми.
- **FR-3.9** Сортировка занятий внутри дня по времени начала.
  КА: занятия выводятся от раннего к позднему.

### FR-4. Карточка занятия

- **FR-4.1** Содержит ученика, предмет, дату, интервал, статус, заметку и ДЗ.
  КА: все поля видны и заполняются.
- **FR-4.2** Заметка и ДЗ — два независимых поля.
  КА: сохранение текста в «что прошли» не влияет на «домашнее задание» и наоборот.
- **FR-4.3** Сохранение заметки и ДЗ без перезагрузки.
  КА: после сохранения текст виден в неделе и после перезапуска.
- **FR-4.4** Действие «Перенести»: выбор новой даты и времени.
  КА: перенос 15.09 18:00 → 17.09 19:00 оставляет карточку 15.09 в статусе
  «перенесено» и создаёт занятие 17.09 19:00 с тем же учеником.
- **FR-4.5** Действие «Отменить» с подтверждением.
  КА: после отмены занятие остаётся в неделе с пометкой «отменено».
- **FR-4.6** Действие «Проведено».
  КА: после нажатия статус меняется, баланс уменьшается на 1.
- **FR-4.7** История переносов видна в карточке.
  КА: у перенесённого занятия указаны исходная дата и новая дата переноса.
- **FR-4.8** Конечные статусы нельзя отменить обратным действием.
  КА: у занятия в статусе «отменено» или «перенесено» действие «Проведено»
  недоступно с понятным объяснением.
- **FR-4.9** Занятие с неизвестным учеником не открывается как рабочая карточка.
  КА: битая ссылка показывает состояние ошибки, а не пустую форму.

### FR-5. Учёт предоплаты

- **FR-5.1** Запись оплаты: количество занятий и дата.
  КА: оплата 4 занятий 01.09.2026 увеличивает баланс ученика на 4.
- **FR-5.2** Количество оплаченных занятий — положительное целое.
  КА: 0, дробное и отрицательное значения отклоняются.
- **FR-5.3** Дата оплаты не может быть в будущем.
  КА: выбор завтрашней даты отклоняется с сообщением.
- **FR-5.4** История оплат видна в карточке ученика с датами и комментариями.
  КА: две оплаты отображаются обе.
- **FR-5.5** Баланс пересчитывается, а не хранится.
  КА: изменение исходных данных и перезагрузка дают один и тот же баланс.
- **FR-5.6** Отмена и перенос не меняют баланс.
  КА: ученик с балансом 4, одно занятие отменено и одно перенесено → баланс 4.
- **FR-5.7** Проведённое занятие при нулевом балансе разрешено, баланс уходит в минус
  и показывается как долг.
  КА: баланс 0, отмечаем занятие проведённым → баланс −1, видно «долг: 1 занятие».

### FR-6. Персистентность и целостность данных

- **FR-6.1** Все изменения сохраняются сразу и переживают перезагрузку страницы.
  КА: добавленное занятие остаётся после перезагрузки.
- **FR-6.2** Перенос сразу отражается в недельном виде без ручного обновления.
  КА: перенос отражается в том же экране.
- **FR-6.3** Схема хранилища версионирована, при изменении выполняется миграция.
- **FR-6.4** Повреждённые или неподдерживаемые данные не удаляются молча:
  исходный JSON сохраняется в резервный слот, интерфейс показывает понятное
  состояние ошибки.
  КА: при повреждённом хранилище данные не пропадают безвозвратно.
- **FR-6.5** Недоступное хранилище не оставляет активными действия, которые
  нельзя сохранить.
  КА: при недоступном хранилище форма создания недоступна, объяснение видно.
- **FR-6.6** В исходном коде нет ключей, токенов и персональных данных.

### FR-7. Качество и выпуск

- **FR-7.1** Есть команды `dev`, `lint`, `typecheck`, `test`, `build`.
  КА: все команды завершаются успешно.
- **FR-7.2** Доменная логика покрыта unit- и integration-тестами, вертикальный
  сценарий — UI-тестами.
- **FR-7.3** `README.md` содержит инструкцию запуска, стек, разбор архитектуры,
  разделы «Данные и приватность» и «Безопасность».
- **FR-7.4** `AGENTS.md` описывает источник истины, инварианты и проверки.
- **FR-7.5** Приложение опубликовано и доступно по ссылке.
- **FR-7.6** В репозитории есть скриншоты ключевых экранов на синтетических данных.
- **FR-7.7** Приложение устанавливается на телефон как PWA и работает офлайн.
- **FR-7.8** Опциональный ИИ-модуль: по заметке предлагает короткое ДЗ,
  репетитор правит и сохраняет. В MVP по умолчанию выключен, не требует ключа
  и не блокирует остальные сценарии.

## 9. Нефункциональные требования

- **NFR-1.** Мобильный интерфейс, пригодный для работы одной рукой: основные

  размер касания.

- **NFR-3.** Все интерфейсные тексты на русском языке.
- **NFR-4.** Операция в неделе (создание, перенос, отмена) визуально отражается

- **NFR-5.** Данные хранятся локально и не отправляются по сети.
- **NFR-6.** Состояние занятия различимо без зависимости только от цвета.
- **NFR-7.** Ошибки хранения обрабатываются без молчаливой потери данных.
- **NFR-8.** Код содержит unit-, integration- и UI-тесты доменной логики
  и основных пользовательских потоков.
- **NFR-9.** Окружение: современный браузер на Windows 10/11, мобильный браузер

- **NFR-10.** Сборка публикуется статически; серверная часть отсутствует.
- **NFR-11.** Приложение работает офлайн после первого открытия.

## 11. Критерии готовности MVP

Приёмочный сценарий. Все шаги выполняются последовательно:

1. Создать ученика: Иван, Физика, контакт, ставка 1200, синий цвет.
   КА: ученик появился в справочнике.
2. Записать оплату 4 занятия с датой сегодня.
   КА: баланс ученика 4.
3. Создать серию: вторник, 18:00, 60 минут, старт сегодня, без даты окончания.
   КА: в неделе видны занятия по вторникам.
4. Создать разовое занятие в четверг 19:00 на 90 минут.
   КА: занятие появилось в четверг.
5. Попытаться создать занятие без выбора ученика и без времени.
   КА: форма не отправляется, показано сообщение.
6. Попытаться создать второе занятие с пересекающимся интервалом.
   КА: отклонено с понятным сообщением.
7. Перезагрузить страницу.
   КА: ученик, оплата, серия и разовое занятие на месте.
8. Перенести занятие вторника 18:00 на среду 19:00.
   КА: занятие осталось во вторнике в статусе «перенесено», новое занятие
   появилось в среду, в карточке видна история переноса.
9. Отменить разовое занятие в четверге.
   КА: оно осталось в неделе с отметкой «отменено», визуально отличается,
   баланс не изменился.
10. Отметить одно занятие проведённым и записать заметку и ДЗ.
    КА: статус изменился, баланс стал 3, заметка и ДЗ сохранились отдельно.
11. Проверить недельный итог.
     КА: видны количества запланированных, проведённых, отменённых и
     перенесённых занятий, остаток предоплаты, сумма к оплате за неделю
     в рублях, а при отрицательном балансе — долг.
     Отменённое и перенесённое занятия в сумму к оплате не входят.
12. Провести занятие при нулевом балансе.
    КА: операция разрешена, баланс ушёл в минус и показан как долг.
13. Закрыть серию и нажать «достроить» у другой.
    КА: закрытая серия не создаёт новых занятий, открытая продлилась без дублей.
14. Повредить данные в хранилище и перезагрузить.
    КА: показано состояние ошибки, исходный JSON сохранён в резервном слоте.
15. Запустить `lint`, `typecheck`, `test`, `build`.
    КА: все команды успешны.
16. Открыть приложение на телефоне, установить как PWA, работать офлайн.
    КА: приложение открывается без сети, неделя и карточка занятия читаемы,
    горизонтальной прокрутки нет.

## 12. План проверки

### 12.1. Unit-тесты домена

- валидация обязательных полей занятия и ученика;
- отказ при пустом имени и при неположительной ставке;
- пересечение интервалов: полное, частичное, касание границы, без пересечения;
- генерация серии: границы 4-недельного горизонта, `startsOn`, `endsOn`,
  повторный вызов без дублей;
- закрытие серии останавливает генерацию;
- перенос: правильные связи, сохранение полей, запрет переноса в прошлое,
  запрет переноса в занятие с пересечением;
- отмена: перевод в конечный статус, невозможность повторного `done`;
- баланс: оплата увеличивает, `done` уменьшает, отмена и перенос не меняют,
  баланс уходит в минус, пересчёт после перезагрузки;
- недельные границы: Пн–Вс, первая и последняя неделя месяца, годовая граница,
  високосный год;
- недельный итог: подсчёт по трём статусам.

### 12.2. Integration-тесты хранилища

- запись и чтение всех четырёх сущностей;
- персистентность после перезапуска;
- версия схемы и миграция;
- обработка повреждённых данных и отсутствующего хранилища;
- сохранение исходного JSON в резервный слот;
- недоступное хранилище: форма недоступна, объяснение видно;
- целостность связей: удалённый ученик, потерянная серия, оборванная связь переноса.

### 12.3. UI-тесты

- создание ученика и проверка формы;
- создание разового занятия и серии;
- неделя с занятиями, переключение недель, пустая неделя;
- перенос и отмена с обновлением недели;
- сохранение заметки и ДЗ, их независимость;
- отметка «проведено» с пересчётом баланса;
- панель недельного итога;
- мобильные состояния на 320 px;
- состояния ошибки без потери введённых данных.

## 14. Риски и открытые вопросы

### 14.1. Риски

1. **Серии — основной источник багов.** Пересечения, отмена перенесённого занятия,
   генерация вперёд и закрытие серии требуют обязательного покрытия тестами.
2. **ИИ в клиентской PWA требует API-ключа**, а ключ в `localStorage` хранится
   в открытом виде. Решение владельца продукта от 2026-09-26: ИИ-модуль не
   входит в MVP и остаётся выключенным, ДЗ репетитор пишет руками, сеть не
   используется. Если модуль вернут в скоуп, ключ должен вводить сам
   репетитор, а без ключа ручной ввод не блокируется (A1 + FR-7.8).
3. **Персональные данные учеников** (имя, контакт) хранятся в открытом
   `localStorage`. Нужно предупреждение в README и в пустом состоянии.
4. **Смена origin** (домен, протокол, порт, браузер) создаёт отдельное хранилище —
   прежние данные не появятся автоматически. Отдельный пункт в README.
5. **Согласие владельца продукта.** Требования, помеченные в §4 как допущения,
   действуют только после подтверждения.

### 14.2. Открытые вопросы

1. Нужна ли отмена в один клик или с подтверждением? Решение: с подтверждением.
2. Нужен ли одновременный просмотр на двух вкладках? Решение: нет, в P2.
3. Нужна ли сортировка учеников в неделе? Решение: по времени начала занятия.
4. Нужна ли отметка «пропущено учеником»? Решение: нет, достаточно `cancelled`.
5. Нужен ли прогноз дохода за месяц? Решение: нет, в P2.
6. Локализация: только русский, подтверждено (NFR-3).
7. Нужна ли печать расписания или экспорт в PDF? Решение: нет, в P2.
8. Напоминания: в брифе они есть в строке «Результат», но отсутствуют в
   «Составе MVP». Решение владельца продукта от 2026-09-26: оставить вне MVP,
   P1. Push-уведомления не добавлять без отдельного решения по scope.
9. Что считать «суммой к оплате» в итоге недели? Решение владельца продукта
   от 2026-09-26: стоимость неотменённых занятий недели плюс отдельная строка
   долга, а не остаток предоплаты в рублях.

| 2026-09-26 | Долг — отдельная строка недельного итога | Баланс предоплаты остаётся в занятиях, а долг показывается деньгами по ученикам недели с отрицательным остатком |
